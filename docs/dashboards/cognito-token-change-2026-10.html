Cognito token change: what it means for the Maps admin

AWS notice, "Additive changes to Amazon Cognito tokens and OIDC metadata". Checked against the code on 2026-10-18.
No action needed. Do not opt out. Our code reads only the token fields it needs and ignores everything else, so two new fields do nothing to it. We never read the discovery document AWS is also changing.

What AWS is changing

Login token today

{
  "sub": "…",
  "token_use": "id",
  "custom:role": "editor",
  "exp": 1790003600
}

Login token after Nov 4

{
  "sub": "…",
  "token_use": "id",
  "custom:role": "editor",
  "exp": 1790003600,
  "acr": "urn:cognito:loa:1",
  "amr": ["pwd"]
}

Only additions. AWS does not rename, remove or change any field that is already there. The discovery document (/.well-known/openid-configuration) gets new entries the same way.

Who breaks, and are we one of them?

  1. Server (Lambda) checks the token safe

    lambda/auth-middleware.mjs uses the jose library to check the signature, issuer, audience and expiry. After that it reads by name only: token_use, custom:role, cognito:groups, custom:allowedRanges, email, sub. Nothing checks for unexpected fields, so acr and amr are ignored.

  2. Browser (admin page) reads the token safe

    admin/auth-service.js decodes the token as plain JSON and reads the same named fields to show the right role. Unknown fields are ignored.

  3. Discovery document not used

    We never fetch openid-configuration. Signing keys come straight from jwks.json, which is not changing.

  4. Bigger tokens safe

    Tokens grow by about 50 bytes. They are kept in browser session storage and sent in a request header. Neither has a size limit we are close to.

If something does go wrong after Nov 4

Sign-in or saves suddenly fail with "401 Unauthorized". This is unlikely, given the checks above. If it happens, open an AWS Support case to opt out temporarily, then look at verifyToken in lambda/auth-middleware.mjs.
